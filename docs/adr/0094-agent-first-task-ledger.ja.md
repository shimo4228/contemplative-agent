# ADR-0094: エージェント優先のタスク台帳 — store / journal / projection

## Status

superseded-by ADR-0095（store と claim journal は規約として存続。projection・aging・candidate intake・4 週間の計測は 2026-08-16 に退役）

## Date

2026-08-15

## Context

タスク台帳は、この repo の gitignored な notes ディレクトリ内にある単一 Markdown 表
`TASKS.md` だった（以下のパスはそのディレクトリからの相対。意図的にローカルなので
weekly chain が polling でき、クラウドエージェントにはできない）。本変更前の実測（2026-08-15）:

| 節 | 行数 | 文字数 | 内訳 |
|---|---|---|---|
| Pending | 71 | 64,090 | ready **6 (8.5%)** / blocked 15 / observing 15 / deferred 19 / **done 16** |
| Done / Dropped | 41 | 36,482 | done 40 / decided 1 |

112 行・102,111 文字 — 着手可能な 6 行を探すためにセッションが毎回およそ 68k トークンを
走査していた。完了した 16 行は Pending から一度も掃き出されていない。他 repo の台帳は
最大でも 15k 文字で、この repo だけが 7 倍の外れ値だった。

**読者が変わった。** 著者は表を読むのをやめ、必要ならセッションに説明させる形になった
（2026-08-15 指示）。これは単一表が立っていた足場 —「人間が一望できるビュー」— を
溶かす。rule `akc-cycle.md` は、足場が支えるより阻害し始めたら溶かせと言っている。

挙がった 4 課題は、調査によって次のように読み替わった:

| 申告 | 実際の正体 |
|---|---|
| 修正中に見つかったバグが ready に積まれ、消化が終わらない | **発見**と**起票**が分離していない。見つかった瞬間に恒久的な backlog ノードになる |
| 並行セッションが衝突し状態が分からない | 共有可変ファイルの後勝ち。`claims.py` は誰が握るかを扱ったが、表そのものは未対応 |
| ready が放置される | 着手可能な 6 行が 64k 文字に埋もれていた。ループが人間の起動を待っていた |
| blocked / deferred が注意を削る | 「判断済みで今は動かさない」49 行が恒久的に視界に残っていた |

**外部の到達点（2026-08-15 時点、独立 3 系統の調査 — 自前 1 + 委託 2）。**
loop engineering は 2026 年 6 月に、graph engineering は 7 月に命名された。合意点は
「ループは done と stuck を機械的に区別できねばならない（できないループはトークンを
使い続ける）」と「畳み戻して何も失わないなら graph を loop に畳め」の 2 つ。
そして **3 系統すべてが独立に「fix-now / file / discard の判定規則」と
「work ノード増殖の上限」は未解決と結論した** — 公開された方針も測定も無い。
Claim Plane（arXiv:2607.21909、2026-07-24）は「変更してよいか」には答えるが、
「起票する価値があるか」には明示的に答えない。

外部推奨のうち 3 件は証拠に基づいて採らなかった:

- **散文を 3〜5 行に圧縮する。** 根拠とされた arXiv:2602.11988 は **repository-level** の
  context file の研究でタスク記録は対象外、しかも有害だったのは repository overview で
  instruction は有効に従われていた。さらに arXiv:2607.12161 は tool-output トークンを
  38.4% 削減して billed cost が **6.8% 増加**（r=0.15）、パッチ適用成功率も低下したと
  実測している（prompt-cache が入力コストを支配するため）。効く梃子は圧縮ではなく
  「読まないこと」。
- **Stop hook で sweep を強制する。** ADR-0035 で Stop hook 3 本を配線ごと退役済み。
- **WIP=1。** 著者は意図して並行セッションを運用している。

移行の過程で、これまで不可視だった欠陥が 2 つ出た:

1. **表は GFM として既に不正だった。** 2 行が backtick スパン内に非エスケープの `|` を
   持ち（`` `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW` ``）、1 行が絶対値記法 `|Δ効果|` を
   使っていた。レンダラはこれを余分な列として読み、1 行は 5 セルでなく 8 セルに割れる。
   誰も render しない上、`ledger_condition_scan.py` は最初の 2 セルしか読まないので
   検出されなかった。
2. **並行編集は頻繁だった。** 本セッション中だけで、別セッションが ready 4 行を
   done/decided へ移し、1 行を痕跡なく削除し（`T-CARE-DISSOC`）、その後さらに 2 行を
   追加した — 2 時間の窓の中で。

## Decision

**1. 3 層にする。**

| 層 | 場所 | 正本であるもの |
|---|---|---|
| store | `tasks/T-XXX.md` | 状態と本文（1 タスク 1 ファイル） |
| journal | `claims.jsonl` | 誰が握っているか / 系譜（`claims.py`） |
| projection | `scripts/tasks.py` の出力 | `TASKS.md` は生成物 |

別タスクは別ファイルなので、後勝ちが無関係な編集を黙って落とすことが原理的に起きない。
`TASKS.md` を生成し続けるのは、表を直接 parse する消費者が 1 本だけ存在するため —
`ledger_condition_scan.py`（第 7 決定論 intake、ADR-0093）— そしてその消費者は無改修。

**2. SQLite でなく markdown + lease 付き claim。** SQLite が勝つ軸は 1 つだけ:
atomic claim が「検出」でなく「防止」になる（`UPDATE … WHERE state='ready'` が
敗者に 0 rows を返す）。他の軸はすべてファイル側が有利 — エージェントが `Read` で直接
読める、ツールチェーンが壊れても cold start でも読める、1 ファイルの破損が全体を
道連れにしない、維持すべき schema migration が存在しない。journal が実際に衝突を
記録するまでは、検出 + lease 失効で足りる。

`claims.py` に `--lease-hours`（既定 24）を足す。期限切れの lease は `--force` 無しで
引き継げる。これは同モジュールが元々「自動 release はしない」とした判断と矛盾しない:
lease は **claim 時に宣言される**ので、期限切れの判定に保持者の生存確認が要らず、
したがってその判断が守ろうとした check-then-act race にならない。
STEALABLE（宣言された lease の期限切れ）と STALE（期限の宣言が無いまま古い）は
別物として保ち、引き継ぎを正当化するのは前者だけ。

**3. ready に上限でなく aging。** `stale_after`（既定 21d）動かなかった `ready` は
`candidate` に降格する。上限は溢れるたびに「何を落とすか」を決めねばならず、その判断には
決定者が要る — 台帳を読むのをやめた人間が。時間は決定者を要さず、降格は削除ではないので
間違えても安い。`blocked` / `observing` / `deferred` は aging しない（実在するものを
待っているため）。

**4. 新設する状態は `candidate` 1 つだけ。** aging の降格先であり、作業中に発見した仕事の
入口でもある。skill `task-stocktake` が既に持つ「候補台帳は台帳ではない」原則（wiki-harvest
の候補向けに書かれたもの）を、発見された欠陥へ拡張する形。`observation` は検討して
**入れなかった** — 未測定の機構を 2 つ同時に入れると、後からどちらが効いたか切り分けられない。

**5. 本文は圧縮しない。** 最長行は意図して長い（「この行は状況分析の材料だけを置く —
解法は書かない」）。上記の実測が、圧縮は節約より高くつくと言っている。

**6. fix-now / file / discard の規則はまだ置かない。** `claims.py spawn` は既に `origin` と
`parent` を記録する。規則より先に 4 週間の実データを取る — 今規則を入れると、その規則を
正当化するはずの測定が汚れる。

## Alternatives Considered

**SQLite (WAL) + CAS claim** — HZL / Beads (Dolt) / Gemini CLI Caretaker が収束した形で、
委託調査の 1 本が推奨した案。原理的に否定したのではなく現時点で見送った: 検出を防止に
変える代わりに、直接可読性（全読者が CLI を要する）、migration すべき schema、
破損すると 113 タスク全部を失う単一ファイル、を支払う。`claims.jsonl` が実際に
失われた書き込みを記録したら再検討する。

**ready への WIP 上限** — Decision 3 のとおり。溢れた時の判断に持ち主がいない。

**表への filesystem lock**（Backlog.md の解。同 PR #860 は 2026-08-07 に、修正前は
8 並列書き込みのうち 7 件が黙って失われたと実測している）。彼らの形には正しいが、
彼らは checkout ごとに単一の可変表を保つ。ファイルを分ければ、調停する代わりに競合自体が消える。

**Backlog.md / HZL / tkr をそのまま採用する。** 3 つとも git-native でエージェント可読だが、
どれも weekly chain の配線（watch 注釈 → packet §10）と台帳に触れる 4 スクリプトの
書き直しを要し、その先に得られるのは `tasks.py` が既存の文法に対して提供しているものと同じ。

**`TASKS.md` を正本のまま残して行だけ削る。** 後勝ちに対処できず、実測は削ることが
誤った梃子だと言っている。

## Consequences

**Positive:**

- セッションが読む量が 105,471 字から 242 字（`tasks.py ready`）へ — 移行後の実測で
  **99.77% 削減**。
- Pending 節に完了行がゼロになった（初めて）。掃除が「誰もやらない雑務」でなく構造になった。
- 別タスクは別ファイル: `T-CARE-DISSOC` を消した種類の静かな消失が、無関係な行に対しては
  原理的に再発しない。
- `origin` / `parent` が起票時点で測定可能になった。以前「課題がどこから湧いているか」を
  調べた時は散文への正規表現に頼るしかなく、精度を保証できなかった。
- GFM の欠陥が通過ついでに直る: render はセル内の `|` を **すべて** エスケープし
  （code span 内だけではない — もう 1 つの不正行は `|Δ効果|` を散文で使っており、
  code span のエスケープでは届かない）、5 セルに割れない行は移行を中断させる
  （タスクを半分だけ移行しない）。読み側はそのぶん dialect を区別する — code span 内の
  裸の `|` を許すのは legacy dialect だけで、それを含むのは旧表だけだからである。
  *2026-08-15 に訂正:* 「全ての `|` をエスケープする」だけでは足りなかった。最初の綴りは
  冪等性のためにエスケープ済みの `|` を自分自身へ畳んでおり、そのせいで本文 `a\|b` は
  escaped pipe と同じバイト列に render され、読み戻すと `a|b` になった — rendered ledger を
  store へ戻す唯一の経路で、backslash が黙って消えていた。セルは backslash → pipe の順で
  エスケープし、読みは左から 1 パスに変え、冪等性は捨てた（`render_row` が唯一の呼び出し元で
  あることは module の AST を歩くテストが固定する）。復旧時に知っておくこと: その日より
  **前**に render された台帳は `\\` を含む本文だけ読み戻しがずれるので、同じ commit で
  projection を store から再生成した。併せて受け入れたこと: code span 内の backslash は
  **表示上**二重になる。GFM は表のセル内なら code span の中でも `\|` を解釈するが、
  backslash に対する escape は持たないためである。2 つの要求は両立しない。「読者は agent で、
  このファイルを render する者はいない」という本 ADR の前提が、byte 側を取る根拠になっている。

**Negative:**

- **`TASKS.md` への直接編集は次の render で破棄される。** hook がどのセッションに対しても
  ファイルに触れた時点で告知するが、切り替え前に始まったセッションはその告知を読んでいない。
  これは実在する窓で、承知の上で受け入れた（両方を正本に保つ代替案の方が、drift が
  静かに進む分だけ悪い）。
- `stale_after: 21d` は測定値でなく仮値。coding agent の ready-WIP や discovery-admission
  の方針を比較した公開研究は存在しない。ready 行は `state_since` を移行日にして移行したので、
  最初のコホートは一斉に aging する。
- 同じデータの表現が 2 つになった（store と render）。両者の整合は規律でなく、
  render した表に対して `ledger_condition_scan.py` を再実行し parse 面を比較するテストで
  保たれる。
- `T-CARE-DISSOC` は復元しなかった（著者判断、2026-08-15）。意図的な削除か失われた
  書き込みかは未決のままで、journal はまだ存在しておらずどちらとも言えない。
