# ADR-0075: Observability by Default — リプレイ可能な監査ログは機能と同じ PR で出荷する

## Status

accepted

## Date

2026-07-09

## Context

検証パーサの第 6・第 7 ラウンド修理（[ADR-0062](./0062-create-time-verification-handshake.ja.md)
第 4〜7 amendment）が可能だったのは、`logs/verification-audit.jsonl` が、誰かが失敗を調べ
始める**前から**存在していたからに尽きる。このファイルには実チャレンジ 816 レコード —
base64 の原文 + sha256、通った solver 経路、提出した回答、verify の成否、サニタイズ済み
エラー — が、デバッグ作業としてではなく solver を動かす通常の副作用として蓄積されていた。
このログが「ソルバが変わらないペースで失敗し続けている」という逸話を、ラベル付き
コーパスに変えた: サーバ受理済みの回答は正の ground truth、サーバ却下済みの回答は負の
ground truth を与え、誤答ゼロの hard gate を持つ決定論的オフラインリプレイハーネスが、
文法変更を全過去チャレンジに対して安全にテスト可能にした。

同じ instrument-first パターンは本プロジェクトの他の場所でも既に効いている: caller タグ付き
LLM テレメトリ（`num_predict` 3000→5000 の retune は勘でなく `done_reason=length` 率の実測で
正当化された）、2026-07-06 の観測性ラウンドで入れた distill 部分障害サマリログと metrics の
no-data マーカー、API drift 監視の `api-audit.jsonl`、ADR-0012 承認ゲート履歴の
`audit.jsonl`。いずれも、ログが「後で答えることになる問い」より先に存在していた。

しかしこの実践は暗黙である。プロジェクトの文書化されたチェーンのどこにも、新機能が監査
計装と一緒に出荷されることを要求する記述はなく、将来の機能 —— あるいはそれを実装する
agent セッション —— がログのない能力を追加し、ADR-0062 の amendment 群を可能にした修理
ループそのものを失いうる: リプレイするコーパスがなく、文法やヒューリスティクスの変更を
test する ground truth がなく、「ランダムに失敗する」と「特定の発見可能なパターンで失敗
する」を区別する手段がない。

オーナーが 2026-07-09、第 7 ラウンド修理が「ログが先にあること」の価値を具体例で実証した
直後にこれを提起した。

## Decision

外部 I/O を行う・LLM を呼ぶ・非決定的またはヒューリスティックな判定を行う機能はすべて、
監査計装を**機能本体と同じ PR で**出荷しなければならない — 後追いにしない。

1. **保存先。** `MOLTBOOK_HOME/logs/` 配下の append-only JSONL。権限を絞った書き込み
   ヘルパー（`append_jsonl_restricted`）経由で書く。
2. **可読でなくリプレイ可能。** レコードはオフラインリプレイに足りること: 生入力の保存
   （untrusted テキストは base64 + sha256 で、生テキストのままは不可 — ログの素読みが
   それ自体 prompt-injection 経路になってはならない）、通った判定経路、すべての
   abstain / fallback / 失敗に対するカテゴリカルな理由コード、そして結果。
3. **silent fallback 禁止。** 理由コードの記録なしの fallback / abstain はスタイルの選択
   ではなく欠陥である。
4. **チェーンゲート。** 実装チェーンの Verify ステップ（harness rule `common/planning.md`）
   で問う: 「この機能が誤動作したとき、どのログが理由に答えるか。オフラインでリプレイ
   できるか」。答えがなければ変更は設計に差し戻す。

原則は意図的に 3 層に分ける: CLAUDE.md が開発原則の 1 行（毎セッション必ずロードされ
行動を形づくる）、プロジェクトスキル
[`.claude/skills/replayable-audit-logs`](../../.claude/skills/replayable-audit-logs/SKILL.md)
が設計ノウハウ（レコードスキーマのチェックリスト、リプレイハーネスのパターン、ground
truth の規律、コーパス駆動修理ループ）、本 ADR が根拠と評価基準の正本。

## Alternatives Considered

### バグが出たときに ad hoc にログを足す

却下。コーパスは ground truth として役立つために失敗より先に存在しなければならない。
第 7 ラウンド修理は数週間分のレコードを消費したが、ログ開始が調査時点だったら存在しな
かった。

### 構造化ログ / observability フレームワーク（例: OpenTelemetry）の採用

却下。これは依存フロアを意図的に最小（`requests` + `numpy`）に保つ単一プロセスのローカル
エージェントである。素の JSONL は grep 可能・リプレイ可能・依存ゼロで、tracing フレーム
ワークは必要に見合わない運用面を増やす。

### global harness rule（`~/.claude/rules`）としてエンコード

却下。これは本プロジェクトの I/O・LLM 呼び出し面に固有の実践であり、global rule は同じ
リプレイコーパスの必要を持たない無関係なプロジェクトに漏れる。

### CLAUDE.md の bullet のみで ADR なし

却下。根拠の実証（ADR-0062 の修理チェーン）と評価基準（上の 4 要件）が正本なしに drift
する。リポジトリ規約は設計判断を ADR に置き、CLAUDE.md はポインタのみを持つ。

## Consequences

### Positive

- デバッグがコーパス駆動修理になる: リプレイハーネス、サーバ却下からの負の ground truth、
  実トラフィックから切り出す回帰 fixture — ADR-0062 の evidence ディレクトリが将来の修理の
  テンプレート。
- 機能が「観測可能な失敗の定義」を設計時に得る（最初の障害後の後付けでなく）。
- agent セッションが挙動の主張をライブ実行の再現でなくログで検証できる。

### Negative

- 機能ごとの小さなオーバーヘッド: レコードスキーマの設計、writer 呼び出しの配線、場合に
  よってはリプレイスクリプト。
- ログは時間とともに成長する。Verify ゲートでレビュアーが見る項目が 1 つ増える。

### Neutral / Follow-ups

- ログ成長はコストとして受容する。既存実践と一貫: JSONL は安価で、エピソードログは既に
  研究材料として無期限保持（`no-delete-episodes`）。
- セキュリティ姿勢は不変かつ強化: untrusted コンテンツはログ内で base64 のまま。CLAUDE.md
  セキュリティ方針に既にあるエピソードログ直読み禁止と一貫する。
