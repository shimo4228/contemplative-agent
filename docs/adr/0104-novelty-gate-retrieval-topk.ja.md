# ADR-0104: novelty gate は候補検索の top-k に対して判定する（在庫全部ではない）

## Status

accepted — partially-supersedes ADR-0074

## Date

2026-09-07

## Context

insight の novelty gate（ADR-0074 D6）は「この候補クラスタを既存 skill が既にカバーしているか」を
LLM の 1 コールに問う。これまで各判定チャンクは `{known}` スロットに**在庫全部** — 採用済み
skill ファイルと staged 台帳、2026-09-04 の run 時点で 485 行 — を載せていた。この形には
2 つのコストが付く。

- プロンプトの実測中央値は **32,768 の窓に対して 30,516 推定トークン**
  （`core/llm/backend.py`、入力と出力が共有）。プロンプト全体で窓の 93%、その大半が在庫
  （RFC-0023 は約 7 割と読んだ）。2026-07-18 の週次 run は既に一度窓を溢れさせ 117 クラスタ
  全部を fail-open している — packer が存在する理由がこれ
- 判定が「12 本との見比べ」でなく「干し草から針」になる

RFC-0023 は 2026-09-04 に同じ store で検索を計測した（`docs/evidence/rfc-0023/`）。
**検索は gate になれない**: recall@5 は全アーム（lexical / bm25 / cosine / RRF 融合）で最良
0.61、類似度に閾値を置いてもカバー済みと未カバーは分離しない（singleton の top-1 分布から
取った閾値では `cosine_*` / `bm25_*` アームでクラスタの 85〜100% が「covered」— `rrf` アームは
17〜53% だが設計を救わない。歴史的な LLM 実測の covered 率は 0.186）、そして一般論の skill が
hub になる（`cosine_full`: 3 本が 912 クラスタの top-1 の 28%、`bm25_full`: 1 本で 25%）。
ADR-0074 の「同一テーマ判定に embedding の分離は存在しない」は反証されず再確認された。

この recall は**出荷する構成とは別の構成で測られている**。しかも差は悲観側に効く: 計測は
**57 本の採用済み skill ファイル**（本文全体、中央値 1,775 字）を、reviewer が却下した候補
skill の名指しに対して引いた — top-10 はコーパスの上位 18% にあたる。gate が引くのは
**515 本の在庫行**（`name: description`、判定者が見る行そのもの）に対するクラスタブロックで、
top-10 は上位 2%。dry-run は 2 つの文書表現が置き換え可能でないことも示す（クラスタ top-1 の
p50 は行 0.7358 / ファイル 0.7653）。したがって**出荷構成の recall は未計測**で、0.77 は
最も近い読みとして桁の目安に使い、上界としては使わない。

残る問いは「プロンプトを縮めると判定が変わるか」で、2026-09-05 のリプレイが答えた
（`docs/evidence/rfc-0023/novelty-replay-ab-20260905.md`、90 コール、監査ログから
バイト一致で復元した 1 run・比較可能な 63 クラスタ）:

- 同一アームの揺れの床: 485 行のまま 3 回流すと互いの対称差は平均 **22.0 / 63**、票が割れる
  クラスタは 52%
- アーム間の差（485 vs top-5 / 10 / 15）: **19.3 / 19.8 / 21.5** — 床より小さい。3 つの k も
  互いに区別が付かない
- プロンプト量: 中央値 **30,516 → 4,364（k=5）/ 5,838（k=10）/ 7,141（k=15）** 推定トークン、
  −77〜−86%
- `fail_open_llm`: full アーム 30 コール中 1 件（28.7k トークンのコールが 269 秒後に失敗）、
  top-k 60 コール中 0 件
- リプレイに見えないもの: そもそもカバーする skill が top-k に入っていたか。これが上の recall の
  問いで、この構成では未計測 — 最も近い読み（別コーパスの k=10 で 0.77）では reviewer の
  名指しの約 4 分の 1 が top 10 の外にあり、小さい k ではこの取りこぼしの類は消えない

## Decision

1. **検索は候補生成、判定は LLM のまま。** 各判定チャンクの `{known}` には、そのチャンクの
   クラスタが引いた cosine（nomic）top-k の在庫行の**和集合**を載せる（在庫全部の代わり）。
   スコアで行を捨てる箇所は他に無く、類似度の閾値も導入しない。ADR-0074 の判定者・出力契約
   （`{"covered": [ids]}`）・「迷ったら NEW」の較正・id 検証・chunk 単位の fail-open・人間の
   承認ゲートは不変。プロンプトへの変更は「ここに並ぶのは近いと出た既存テーマであって
   全在庫ではない」の 1 文追加のみ。
2. **k = 10**（`_NOVELTY_TOPK`）。リプレイで k ∈ {5, 10, 15} に差が出なかったので RFC の
   10〜15 の下端に置く: 上げればプロンプトが伸びるだけで測れる利得は無く、下げれば
   カバーする skill が窓から早く落ちる（0.77 の読みは、その構成でも既に reviewer の名指しの
   約 4 分の 1 が top 10 の外だった）。
3. **順位付けの規則**: cosine 降順、同点は name 昇順。検索の doc は描画される在庫行
   （`name: description`）— 判定者が見る text と同じで、プロンプトに載らないものを採点しない。
   チャンクの known 行は在庫の元順序で出力するので、判定者から見て変わる変数は「本数」だけ。
4. **packer は各ブロックにそれが新たに持ち込む known 行だけを課金する。** 同じチャンクの
   別クラスタが既に持ち込んだ行は無料なので、チャンク境界は実際のプロンプトコストに従う。
   加えて 1 チャンクは**クラスタ 10 件**で打ち切る（`_NOVELTY_MAX_CLUSTERS_PER_CHUNK`）。
   空いた約 28k トークンに任せると 2026-09-04 規模で 1 コール ~39 クラスタになり、これは
   誰も測っていない判定レジーム（リプレイは 64 クラスタを 10 チャンク = 約 6.4 件ずつで
   判定した）であり、1 回の fail-open が失う判定も 6 倍になる。
5. **埋め込みが使えないときは在庫全部へ、黙らずに fallback する。** `embed_texts` が失敗する /
   行数が合わない / 非有限またはゼロノルム行を返す（後者は黙って名前順の順位を返す）とき、
   run は従来どおり在庫全部で判定し、`reason=retrieval_unavailable` を WARNING に出し監査にも
   記録する。再試行はしない — gate は週次で、劣化した読みは大きいプロンプトより悪い。
   **この fallback は検索導入前の挙動そのもので、溢れも含めて同じ**: 現在の 515 行では
   在庫だけで budget を超えるため、埋め込みが無い run は 1 件も判定せず全クラスタが
   unjudged で fail-open する（`fail_open_budget`。本 ADR 以前から packer が出していた状態で、
   検索が要る理由でもある）。人間ゲートのレビュー負荷が増えるだけで、テーマが黙って
   落ちることはない。上位 k 行だけの縮小 fallback も検討したが、順位付けのない任意の
   切り出しを候補として見せるのは「候補が無い」と言うより悪いので採らない。
6. **監査ログが「判定者が何を見たか」を言う**（ADR-0075）。各レコードに `known_selection`
   （`mode` topk|full、`k`、`reason`、`embedding_model`）と `inventory_count` を追加。
   `known_themes_count` は**そのチャンクが見た行数**を意味する（prompt を作らない
   `fail_open_budget` は 0）。これで「判定者が見ていなかった」と「見た上で新しいと言った」を
   読み分けられる — 本決定が導入する失敗モードがまさにそこ。

## Review-when

- **候補検索が reviewer の判断を再現しなくなる。** `scripts/retrieval_recall_measure.py` を
  **出荷構成で**（doc = 在庫行、query = クラスタブロック、現在の store）再実行し、
  script 版・コーパス・reviewer の正解集合を 2 回の読みの間で固定したうえで recall@10 < 0.8 が
  2 回続いたとき。2026-09-04 の v1（0.83）/ v2（0.77）はこのカウントを開始しない — 名前解決の
  コードが異なり、コーパスの形も gate のそれと違う。応答は k を広げるか止めることで、
  類似度の閾値ではない。
- **fallback が常態になる**: 土曜ゲートで `known_selection.mode == "full"` が 1 run の
  レコードの過半を占めるとき。直すべきは検索でなく埋め込みへの依存。
- **判定者の covered 率が、これまで gate が出してきた帯を外れる。** 基準: 2026-09-04 の run は
  64 クラスタ中 27 covered（0.42）。リプレイの揺れの床から、1 run の率は良くて ±0.1 の精度
  （同じプロンプト 3 回で 26 / 22 / 27）。2 run 続けて 0.42 ± 0.2 の外に出たら、縮小は
  リプレイに見えなかった何かをしている。（dry-run の 0.186 は別のクラスタ窓の 7 run を
  合算した値で、1 run の基準値ではない。）
- **在庫が増えなくなる**（退役が採用を上回る）**、かつ窓に収まる**: そのとき本機構は不要で、
  調整でなく削除する。

### Consumption plan

本 ADR が足す監査 2 欄（`known_selection` / `inventory_count`）は監査面なので ADR-0101 が効く。

- **(a) 誰がいつ読むか**: 土曜の `/weekly-gate` が、その週の insight run の
  `logs/insight-novelty.jsonl` を読む（チャンク 1 行、既存の `verdict` の数え上げと一緒に）。
- **(b) 何回の読みで何を決めるか**: 上の Review-when の第 2・第 3 トリガ（fallback の過半 /
  covered 率の帯外れ）を**各 2 回の読み**で決める。1 回では何も決めない。
- **(c) 撤去条件**: 機構と一緒に消える — 在庫が窓の内側に戻る（第 4 トリガ、検索ごと削除）か、
  検索が置き換わるとき。土曜ゲート 4 回連続で `mode == "topk"` かつ異常なしなら
  `known_selection` は reason コードだけに畳む（`mode` と `k` は本 ADR から導出できる）。
  `inventory_count` は他のトリガが要る分母なので残す。

## Alternatives Considered

**在庫全部のまま。** 精度でなくコストで却下: 窓の 93% を占めるプロンプトの精度が
4〜7k 版と区別できず、28.7k トークンのコールで `fail_open_llm` が 1 件観測され、store は
増え続けて 2026-07-18 の溢れへ戻っていく。

**検索を gate にする（top-1 類似度が高いクラスタを捨てる）。** 計測で却下: 母集団が分離しない
（`cosine_*` / `bm25_*` アームでは singleton 分布由来の閾値でクラスタの 85〜100% が「covered」、
歴史的な LLM covered 率 0.186 に対して）。hub の読みは「最も曖昧な skill が最も多く抑止する」
と言う（`bm25_full` は一般論 skill 1 本で top-1 の 25%）。ADR-0074 の読みの再確認。

**BM25 と cosine の融合（RRF）。** 却下: v2 の読みではどの rrf_k でも cosine 単独を上回らず
（recall@10 0.76 vs 0.77）、index とパラメータを 1 つずつ増やすだけ。BM25 は計測スクリプト側に
残る。

**k = 15、または run ごとに k を変える。** 現時点では却下: リプレイは k を区別できないので、
大きい k は雑音に対してプロンプト量を払うだけ。run ごとの k は読みが提供していない信号を要る。

**fallback の前に埋め込みを再試行する。** 却下: gate は週次で fallback は「正しいが高い」ので、
再試行は失敗する run を長くするだけ。計測スクリプトが再試行するのは、止まった読みには
fallback が無いから。本番にはある。

## Consequences

- 判定プロンプトは 2026-09-04 規模の store で k=10 のとき ~30.5k → ~5.8k 推定トークンへ落ちる。
  `fail_open_budget` は通常経路では発火しなくなるが、fallback 経路では依然到達可能（D5）。
  扱うコードを残す理由がこれ
- gate の主経路に依存が 1 つ増える: 埋め込みホスト。その障害は旧挙動への**記録された**劣化で
  あって黙った劣化ではない。ただし現在の在庫規模では旧挙動はもう何も判定しない（D5）ので、
  埋め込みが落ちた週は判定が失われ、バッチ全体が unjudged のまま人間ゲートへ来る。これは
  本決定の実運用コストで、`tests/test_insight.py::TestNoveltyFullInventoryFallbackAtScale` が
  pin する
- 旧い形が払っていなかった経常コスト: 毎 run で在庫全体 + クラスタごとに 1 query を埋め込む
  （64 件ずつ、キャッシュ無し = 在庫は毎回埋め込み直す）。515 行なら数秒だが、週次の窓の中で
  常駐している生成モデルと競合する — まさにその状態で 1 回の大きな POST が Ollama に拒否された
  実績があり（2026-09-05、リプレイ script の batching 注記）、バッチが小さいのはそのため。
  在庫ベクトルのキャッシュは無効化の問い（description を編集したら埋め込み直す）を伴う別の
  変更で、ここでは取らない
- **新しい失敗モード**: クラスタの top 10 の外にあるカバー元 skill は判定者に見えないので、
  在庫全部版なら捕まえたかもしれない重複 skill が人間ゲートまで来る。この構成での大きさは
  未計測（Context 参照）で、リプレイが縛るのは**総体**の側 — full アームが全 rep で covered と
  した クラスタは、どの k でも top-k 側の 1 rep 以上が covered にしている。最後の filter は
  人間の承認ゲートのままで、事後にこの型を帰属させる材料が監査の `known_selection`
- `scripts/novelty_replay_ab.py` は 1 run のレコードが在庫を共有していることを要求して復元する。
  これは既存のガードで本変更では触っておらず、top-k の run に向けると異種チャンクを比較せず
  明示エラーで止まる。2026-09-04 run の凍結証拠なので移行しない。
  `scripts/novelty_retrieval_dry_run.py` は `verdict` / `covered` しか読まないので影響なし
- chaos の行が 1 つ増える（F-NOV-6、埋め込みホスト停止。在庫が窓に収まる規模での検査）。
  規模が大きいときの fallback は `tests/test_insight.py` 側で別に pin する。既存の
  fail-open 行は不変
- プロンプトファイルが変わったので ADR-0089 の eval baseline
  （`comment_golden-2026-08-31.json`）は STALE になる。`verify.sh` は advisory として報告し、
  再実行と再承認は人間の判断であって本変更には含めない
- RFC-0023 の**希少レーン**（最も近い skill が遠い singleton を保留して週次で再クラスタ）は
  本変更に含まれず、open のまま
