## 2. 反転 1: 論文を読めていなかった

設計は 08-30 の読みに立っていたが、その読みは arXiv の HTML 版で、HTML 版には Appendix A〜E が無い。
Maintainer の入力を「その日の全件」、Proposer を「1 コール」、Table 4 を「skill の数」、
Maintainer / Proposer を「Claude 級」と読んでいた。4 件とも Appendix か全文照合で初めて崩れる誤りだった
（RFC-0022 Reading 節と RFC-0017「論文記述の訂正」）。

発覚の経路が学びの中心にある。著者が 09-02 に「52 日」「予算詰め」「論文は Opus にも全量入れていないのでは」と
問い、設計を主導した文脈が読み直しても同じ盲点を踏むと判断して、fresh context の別セッションに PDF 28 頁を
全読させた（RFC-0022 の起票理由）。そこで 3 件が確定し、4 件目（モデル級は論文のどこにも無い）は
その照合の中で出た。

学び: 機構を移植する論文は PDF の Appendix まで読む。これは memory に落ちた。もう 1 つは、
読み違いを疑う側の人格を変えることで、同じ文脈に「もう一度読め」と言っても出ない。

## 3. 反転 2: 「忠実」の対象が無かった

設計セッションの入口は「述語を変えるより Wiki-skill の機構をそのまま採用」「できる限り論文と忠実に」だった
（09-01 22:19Z / 22:28Z）。同じセッション内で「Gemma には無理そう。逆にこのクラスでできたら面白い」（23:09Z）、
「なんか忠実実装がそもそも無理な気がしてきた」（23:24Z）と揺れ、並列実験として建てる形に落ちた。

無理の理由が言葉になったのは 09-02 昼。論文の loop は検証スコア（正解との一致率）が層化・trace 選択・
採用判定の 3 箇所を駆動するが、CA に正解が無い。「成功も失敗も判定がないなら完全なランダム」（11:27Z）は
著者の言い方で、判断としては「形は採り、エンジンは採らない」に落ちた（RFC-0017「エンジンを採らない理由」）。

後から見ると、この判断はまだ「形」と「モデル」を混同していた。形を採れば残る自由変数は容量と判定者だと
考え、D4 の日次全件 batch と「小型モデルでも収まるからいい設計」（12:16Z）の 3 則で容量側を詰めた。

窓に収めることは達成したが、それは拘束条件ではなかった。拘束していたのは書き手の register で、
それは反転 3 で初めて見えた。

## 4. 反転 3: 平坦化を形のせいにした（核）

gemma smoke の 9 ページは全部が一般論の型に落ちた。RFC-0017 smoke 節の記録では
"A critical failure mode in advanced computational systems is the assumption that…" で始まる maxim で、
distill の行が持つ一人称と状況が無い。ここまでは観測で、問題はその原因帰属だった。

09-03 13:22Z、判断役は「閉じてよい。失敗の原因が gemma の力不足ではなく形にあると読めるから」と書いた。
同じ発言の末尾に「一つだけ迷いがあるとすれば、opus アームを一度も回していないこと。散文形でも大きな
モデルなら平坦化しないなら、原因の一部はモデルにある」とも書いている。

迷いは言葉になっていたが、結論の後ろに置かれた。著者は「閉じていいかも」と受け、
翌分に「Opus アームも回して検証しよう」と決めた。

opus アームは同じ 3 日、同じ形、同じ 32k 窓で回した。結果は反転し、9 ページ全部が具体的で行動を変える
内容だった（要旨は RFC-0025 Motivation 3。本文は他 agent の handle を含むので非公開）。
一方 M-a は gemma 0.80 に対して opus 0.6786 で、counter だけ見れば gemma の方が良い。

分けたのは散文の register で、どの counter も測っていない。ADR-0103 Context はこれを「M-a は決め手ではない、
後の読者が誤読しないためだけに記録する」と書いた。metric が測っていないものを言葉で書き残すことが、
凍結した JSON 2 本に対する唯一の補正になっている。

学び 1: 原因帰属の前に対照アームを回す。「形が悪い」と「モデルが弱い」は同じ観測を出すが、
後続の仕事がまるで違う。形なら JSON 化や topic 層で形を作り直す仕事になり、モデルなら形は保存して
退役し、モデルが変わる日の再開材料を残す仕事になる。

実際に後者へ進めたのは対照があったからで、無ければ 09-03 未明に検討していた形の再設計へ進んでいた。

学び 2: 迷いの節が結論より前に立つべきだった。判断役の発言は正しい迷いを含んでいたのに、
文の構造が「閉じてよい、ただし」だった。著者が「回して検証しよう」と言い直したから救われたが、
これは著者の判断で、判断役の文構造は改善の余地がある。

学び 3: metric が測っていないものを言葉で書く。M-a は preregistered で 0.9 の線があり、
その線を越えていないのに gemma が「良い」側に見える構造になっていた。counter の設計時に
「この counter が拾わない失敗はどれか」を 1 行書くことが、次の計器の設計に持ち越す規律になる。

## 5. 反転 4: 第 2 の読者は第 1 の読者と同じ物を書いた

09-03 13:00Z、著者が wiki ページを見て「これほぼ現状のスキルファイルではないか？」と言った。
判断役が p-0003 と skill `analyzing-systemic-governance-loops` を並べると、register も粒度も同じだった。
どちらも gemma が episode 1〜2 件を「一般的なシステム設計の教訓」に持ち上げた文で、蓄積は効いていない。

gemma Proposer dry-run の唯一の提案がこれを裏書きした。p-0001 を skill `detecting-abstraction-decay-in-context`
に append する提案で、共通項は「証拠が足りない」という抽象語だけ、anchor は本文に無い description 行を指した
（RFC-0025 Motivation 2）。一般論に一般論を足しても一般論のままだった。

ここで著者の評価が転回した。「Wiki の平坦化を見ていたら、今の 1 エピソードからパターン生成する knowledge は
悪くない気がする」（13:30Z）。wiki は insight 抽出を良くする道具として建てたのに、退役の過程で
現行 insight の評価を上げた。

学び: insight → skills に足りなかったのは抽象化の段ではない。足りないのは既存 skill との距離（RFC-0023 が
候補検索で扱う）と、抽出そのものの register（RFC-0024 が自由記述とコール分割で扱う）だった。
「散文を LLM に書き直させる中間物」は、小型モデルでは同型の skill をもう 1 本増やすだけになる。

## 6. 判断役の推奨と著者の選択が割れた点

09-03 22:38Z の AskUserQuestion で判断役は「opus で wiki を生かす（推奨）」を第 1 選択肢に置いた。
著者は「wiki は閉じる、gemma のまま」を選んだ（22:57Z）。根拠は ADR-0069 で、本番生成は 16GB の
無人運用で gemma4:e4b に固定されており、episode 本文を cloud に出すことは security by absence を緩める。

判断役の推奨は「形は正しい」という読みを最短で活かす経路で、著者の選択は本番の前提を動かさない経路だった。
ADR-0103 はこの割れを Alternatives Considered「Run the wiki on opus」として残し、Review-when の第 2 条件
（cloud へ出す判断が別途下る）に生かしている。推奨が消えたのでなく、発火条件付きの選択肢として保存された。

sunk cost は理由にしなかった。ultrareview 済みの packet A / A+1 が丸ごと消えることを ADR-0103 Consequences は
"Sunk cost is not a reason to keep them (Emptiness), but the cost was real and this ADR is where it is recorded"
と書いた。費用を判断に使わず、記録だけ残す形は、公理の適用として妥当だったと思う。

## 7. 副次の学び

- **一回限りの選択が規則化した。** Review に `/code-review ultra` の無料枠を使うと設計セッションで決めたことが、
  RFC-0022 実装で指示なしに発火した。著者の訂正「RFC は別にいいよ。Memory は困る」が、
  memory の「状況依存の選択を恒常規則にしない」として残った。
- **RFC-0017 は 57 行から 569 行に育った。** 設計 D1〜D15、逸脱表、訂正節 4 本、smoke 読み、Next action を
  1 ファイルに抱えた。設計と観測記録を同居させると読み手が「今の正本はどこか」を探すので、
  次は観測記録を evidence 側に置く。
- **ADR 番号が衝突した。** branch 上の退役 ADR が 0102 を取り、同日 main に別件の 0102 が入ったので
  merge で 0103 に採番し直した。未 merge の branch に ADR を置くと番号は予約されない。
- **3 則は書き直された。** 「索引は安い投影 / code が列挙し model は enum で名指す / サンプルでなく batch」は
  窓に収める規律だった。退役 branch で skill `llm-pipeline-layering` の同節は「add one, judge apart,
  don't rewrite prose」になり、窓でなく register を主語にしている。
- **引用の幻覚は全文 preload で 0 になった。** S4 smoke の M-a 0.20（SOURCES_EMPTY / PAGE_NOT_FOUND）は
  packet A の 1 形で消えた。ただしその形が窓を毎日削る側の原因になった。
- **障害 2 件、どちらも silent fallback は無かった。** gemma の day 3 batch 3 は Ollama read timeout
  （1,200 秒）で fail_closed し、retry 無しで catch-up に任せる設計は正しく働いた。opus アームの初回は
  Anthropic API 500 で 3 日とも fail_closed し、同日夜の再起動で完走した（失敗 run は JSON に無く、記録はセッションログのみ）。

## 8. 残る問い（解決したふりをしない）

- **−2.8k / 日は n=2 の外挿。** 差分 3,541 と 2,015 の平均で、2 点は 75% 違う。「約 10 日で窓が尽きる」は
  この外挿からの計算で計測値ではなく、ADR-0103 Context の書き方をここでもそのまま置く。
- **「形は正しい」は 1 アーム 3 日の読み。** opus の 9 ページが「行動を変える」というのは判断役と著者の通読で、
  実際に skill として採用され Moltbook での挙動が変わった計測は無い。Proposer の提案が人間ゲートを
  通った回数は 0 で、形の正しさは prior であって証拠の強さは smoke 1 回分。
- **大型モデルの wiki が成立する側の実例は未検証。** RFC-0025 Prior art が Obsidian vault の LLM wiki
  （Opus、87 ページ）を引くが、この振り返りではそれを読んでいない。
- **「動的に編集され続ける wiki が唯識的」の直観はどこへ行ったか。** 09-02 22:39Z に著者が topic 層と
  View 固定を却下した理由で、「変わりゆく視座を過去時点で固定することになる」と言った。wiki を退役した今、
  この直観を受ける機構は無い。knowledge の per-episode pattern は動的だが、それを編集し続ける段は無く、問いとして残す。
- **RFC-0024 は draft のまま。** 抽出の register を直す側の仕事は、RFC-0023 の順序条件の後ろで待っている。
  反転 4 の学びの半分はまだ実装されていない。
- **判断役の文構造。** 反転 3 の学び 2 は判断役（このハーネス上の Claude）の書き方の問題で、
  skill か rule に落とすべきかを決めていない。1 回の観測なので、まだ落とさない。
