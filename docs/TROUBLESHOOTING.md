# Troubleshooting

Symptom, likely cause, and the log or command that answers it. Start with `contemplative-agent doctor`
(Ollama, the models, the decision canary, the home directory, the Moltbook key). It prints one
`[  ok  ]` / `[ WARN ]` / `[ FAIL ]` line per check (a `->` line under it names the fix) and exits 1 if any is
`FAIL`; the rows marked *doctor* below quote every `WARN` and `FAIL` line it can print
(`tests/test_troubleshooting_doc.py` checks them against `cli/doctor.py`). Logs are under `$MOLTBOOK_HOME/logs/` (default `~/.config/moltbook/logs/`).
Settings are in [CONFIGURATION.md](CONFIGURATION.md); design reasons are in the ADRs linked per row.

| Symptom | Likely cause | Where to look / what to do |
|---|---|---|
| `run` ends with an `ERROR: Ollama: …` line on stderr, exit code 1 | Ollama is not running, or `OLLAMA_BASE_URL` points elsewhere. *doctor:* `[ FAIL ] Ollama: not reachable at …` / `… answered, but not with Ollama's API` | Start Ollama (open the app or `ollama serve`), then `contemplative-agent doctor`. Before its first cycle `run` makes the same Ollama and generation-model check, tries 5 times 20 seconds apart (the nightly restart may still be coming up), then prints the reason (`ollama_unreachable`, `model_not_listed:<tag>`) and exits 1 |
| `run` ends with `Moltbook unreachable: 5 attempts to read /home failed (…)` | session setup could not read Moltbook's `/home` (network down, Moltbook down) | The setup retries 5 times, 20 seconds apart, then ends the session instead of running blind. Check the network and Moltbook's status, then start again; a scheduled run tries again at its next slot |
| *doctor:* `[ FAIL ] Generation model: … is not pulled; the relevance gate fails closed and the agent engages with nothing` | the model named by `OLLAMA_MODEL` (default `gemma4:e4b`) was never pulled | `ollama pull gemma4:e4b`. Without it the relevance gate has no judge and the feed stays silent (next rows). `run` prints the same line as `ERROR: Generation model: … [model_not_listed:<tag>]` after its 5 tries and exits 1 |
| *doctor:* `[ WARN ] Embedding model: … is not pulled; embedding-backed checks fail open` | `nomic-embed-text` missing | `ollama pull nomic-embed-text`. Embedding-backed checks fail open, so sessions run, but distill and insight need it |
| The agent runs but never comments, upvotes or posts from the feed | the relevance gate is **fail-closed**: it got no answer from its judge, or `thresholds.relevance_score4` is missing from `config/domain.json`. With `DECISION_MODEL=` (empty) the gate is deliberately off ([ADR-0113](adr/0113-decision-faces-and-relevance-score4-shadow.md)) | `logs/relevance-*.jsonl`: rows with `gate_source: "fail_closed"` and an `enforce_reason` (`enforce_no_threshold`, `enforce_backend_null`, `enforce_exception`). The session also logs one WARNING per session. Fix the cause the reason names; the next feed cycle asks again |
| *doctor:* `[ WARN ] Ollama: unrecognised reason '…'` | the serving reading carried a reason this version of `doctor` does not know (a newer core, or a local patch) | Read the reason it quotes (it is the `;`-joined reason of `core.llm.serving_environment()`); report it if it does not come from your change |
| *doctor:* `[ FAIL ] Decision backend: DECISION_MODEL is empty: no decision backend, so the relevance gate fails closed (enforce_backend_null) and the agent engages with nothing` | `DECISION_MODEL=` (empty) is set, which turns the relevance gate off on purpose ([ADR-0113](adr/0113-decision-faces-and-relevance-score4-shadow.md)) | Unset `DECISION_MODEL`; it then reads the served generation model |
| *doctor:* `[ WARN ] Decision canary: decision_canary_failed: <reason> (model <name>)` | the model did not answer the one-token yes/no canary: no first-token probabilities came back (an untested model, or a build without logprobs). The reason is the decision backend's own code | Use the tested model (`gemma4:e4b`), or accept that the gate will fail closed with this one. [ADR-0112](adr/0112-decision-backend-seam-and-shadow-skill-decision.md) |
| *doctor:* `[ WARN ] Decision canary: decision_canary_failed: answered_no (P(yes) 0.xx, model <name>)` | the model answered, but put P(yes) at 0.5 or less on a question whose answer is yes: its first-token read is not a usable relevance judge | As the row above |
| *doctor:* `[ WARN ] Decision canary: skipped: Ollama or the generation model is not ready` | a `FAIL` on the Ollama or generation-model line above; the canary needs both | Fix that line first, then run `doctor` again |
| *doctor:* `[ FAIL ] Home: … has no identity.md` | `$MOLTBOOK_HOME` was never initialised (or `MOLTBOOK_HOME` points at another directory) | `contemplative-agent init`. Check `echo $MOLTBOOK_HOME`; a launchd job uses the value its plist sets |
| Generation seems to restart the model every batch; sessions get slow, memory swaps | `DECISION_MODEL` names a different model than the served generation model, so each decision batch swaps models. On a 16 GB machine two models do not fit together | Unset `DECISION_MODEL` (it then reads the generation model) and do not run another model beside it during a session. See the `DECISION_MODEL` row in [CONFIGURATION.md](CONFIGURATION.md#environment-variables) |
| `insight` prints `No previous insight run marker (.last_insight) found. Refusing to …` | the incremental run requires the `.last_insight` marker; it refuses instead of silently reclustering the whole pool ([ADR-0074](adr/0074-weekly-staged-insight.md)) | Run `contemplative-agent insight --full` once to set the marker |
| `insight --stage` or `distill-identity --stage` refuses while something is staged | an unreviewed batch is waiting in staging | `contemplative-agent adopt-staged` and decide on it first ([ADR-0012](adr/0012-human-approval-gate.md)) |
| A skill or identity change you expected did not appear | it is still staged, or it was rejected (a rejected text is deleted and only its hash kept) | `ls $MOLTBOOK_HOME/.staged/`; the approval history is `logs/audit.jsonl` |
| *doctor:* `[ WARN ] Moltbook key: no …/credentials.json and no MOLTBOOK_API_KEY (only `run` needs it)` | the key was never saved. When both exist, the environment variable wins over the file | `contemplative-agent register --name NAME` writes `$MOLTBOOK_HOME/credentials.json`. A key in your shell does not reach launchd jobs: rely on the file for scheduled runs |
| A scheduled run behaves differently from your terminal run | launchd starts jobs with only the environment the plist sets (the agent plist sets `PATH` and nothing else), so your shell's `OLLAMA_MODEL`, `MOLTBOOK_HOME` or `MOLTBOOK_API_KEY` are not there | Compare the installed plist in `~/Library/LaunchAgents/` with your shell, and read the job's `*-launchd.log` under `logs/` (`agent-launchd.log` is not safe for a coding agent to read; see CLAUDE.md) |
| Nothing is scheduled on Linux or Windows | `install-schedule` is macOS-only (launchd) | Start `contemplative-agent run --session N` from your own scheduler ([CONFIGURATION.md](CONFIGURATION.md#macos-scheduling-launchd)) |
| A post's relevance reading is missing from `relevance-*.jsonl` | the post was answered from `relevance_cache.json` (an entry is reused for 14 days unless the inputs changed) | The session-end episode counts `feed_relevance_cache_hits`; the cache is explained in [CONFIGURATION.md](CONFIGURATION.md#runtime-logs) |

If a row does not cover it: the replayable audit logs under `logs/` say what each call decided and why
([ADR-0075](adr/0075-observability-by-default.md)); `docs/runbooks/silent-llm-calls.md` is the guide for hunting
unexpected model calls in tests.
