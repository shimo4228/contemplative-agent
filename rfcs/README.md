# RFCs

この repo の提案と作業項目の公開台帳 — 1 エントリ 1 ファイル `NNNN-slug.md`、ID は
`RFC-NNNN`。フル RFC の提案から小さな作業項目まで同居する。**state は各ファイルの
frontmatter が唯一の正本**。下の表は `scripts/rfc_index.py` が frontmatter から生成する（手で編集しない）。

起票の手順と規約（足切り・採番・様式・公開規約）の正本は
[skill: rfc-writer](https://github.com/shimo4228/claude-harness/blob/main/skills/rfc-writer/SKILL.md)、状態語彙は
[skill: task-stocktake](https://github.com/shimo4228/claude-harness/blob/main/skills/task-stocktake/SKILL.md)、判断は
[claude-harness ADR-0049](https://github.com/shimo4228/claude-harness/blob/main/docs/adr/0049-unify-task-ledger-into-public-rfcs.md)。
上のリンクは詳細。**このページだけで台帳を読むための最小規約**は次の 5 行（P2-03.4。
harness に触れなくても state と昇格の有無が解釈できる）:

1. **state の語彙。** `draft`（起票直後、採否未決）→ `accepted`（着手してよい）→ `done`（実装・採用済み）。
   着手中は `in_progress`、途中で待つ間は `blocked`。**終端**は `done` / `resolved`（前提が消えて変更なしで片付いた）/
   `withdrawn`（起票者か owner が取り下げた）/ `obsoleted`（別の決定に置き換わった）/ `rejected`。`state:` は
   1 語で、その state に入った日は `state_since:` に書く。終端のファイルは消さずその場に残す（却下理由ごと残るのが公開判断記録の価値）。
2. **blocked の 3 行様式。** 本文の「着手条件」節に `再開条件:` / `照合先:` / `成立時:`（成立したら
   どの state になるか）を各 1 行で書く。triage の照合節は日付つきでこの下に積む。
3. **RFC → ADR の昇格条件。** 本番挙動・スキーマ・ゲートを変える決定が固まった時、決定を
   `docs/adr/` に ADR として書き、RFC は `done` にして ADR へリンクする（例: 0028→ADR-0106、
   0031→ADR-0108、0037→ADR-0110、0042→ADR-0111、0046→ADR-0113）。読み・運用記録・取り下げ
   だけで終わる RFC は昇格しない。
4. **RFC に残すもの。** 提案の理由、読み（数字と窓）、再開条件、triage の照合、終端の理由。
   決定そのものは ADR、測定の生データは `docs/evidence/`。
5. **frontmatter。** `state` と `state_since` は必須。無人チェーンの起票は `origin: gate` と
   `filed_by: weekly-<end-date>[-<HHMMSS>]`（起票した run）を持つ。`review-when:` は再読の条件。
   state ごとに増える必須欄は次節（test が検査する）。state の正本は各ファイルの frontmatter で、下の表は索引にすぎない。

## 本体が検査する frontmatter（`tests/test_rfc_frontmatter.py`）

規約の本文は rfc-writer 側。この repo は欄の存在と形だけを test で守る（`scripts/rfc_index.py --validate` でも同じ検査）:

- `draft` は `state` と `state_since` だけで通る（無人 chain の起票。`title` / `review-when` / `alignment` は accepted 以降の必須で、土曜ゲートが埋める）
- `title` / `state`（1 語: draft / accepted / in_progress / blocked / done / resolved / obsoleted / withdrawn / rejected）/ `state_since`（その state に入った日）
- `review-when` — accepted 以降で終端（done / resolved / obsoleted / withdrawn / rejected）以外は必須
- `decide_by` / `next_check` — blocked は必須。`decide_by` までに解除条件が成立しなければ withdraw か問いを小さくする。`next_check` より前は triage が追記も照合もしない
- `admitted-by: <名前> <日付>` — accepted / done は必須。記録が無いものは推測せず `unrecorded`。`decided-by` は任意で同じ形
- `alignment` — open で draft より先（accepted / in_progress / blocked）は必須。repair / instrument / capability-growth / value-steering-risk（ADR-0080 の審査軸）。`decision_needed` は 1 行の問いで、下の awaiting-owner 節に出る
- 本文の `## Status` 節は state 語を先頭に置くなら frontmatter と一致させる。経緯の記録は `## 決定の記録` 節に書く。節の先頭は定型の 1 行（現在の state は frontmatter）で、その次に frontmatter と違う state 語を日付なしで置かない

## 照合節の様式（`docs_consistency_scan.py` が検査する範囲）

task-triage loop（水 17:07 / 土 14:07 の無人 cycle、契約は [docs/CYCLES.md](../docs/CYCLES.md) の
Operating model「Task-triage loop contract」）が各 RFC に追記する節の様式。

- 見出し: `## YYYY-MM-DD triage 照合 (by: judge)`。手動 cycle をオーナーが回したときは `(by: owner)`。
  `by:` は `judge` | `owner` の閉じた語彙
- 本文に 1 行 `verdict: <値>` を持つ。値は閉じた語彙で、`dead-band`（変化なし。次の読みの日付を書く）/
  `hold`（前提を確かめ、状態を維持する。理由を書く）/ `ready`（前提を検証済み。採否はオーナーの digest）/
  `ask-owner`（オーナーの判断が要る）/ `stale`（前提が崩れた。終端の提案はするが、設定はオーナー）
- オーナーの回答は別の節 `## YYYY-MM-DD 著者回答 (by: owner)` に書く。`state:` の変更はこの節の後に限る
- weekly の findings 側（RFC の外）は、各 F-finding に `severity`（`high` | `medium` | `low`）と
  `claim_type`（`defect` | `measurement` | `design`）を同じ形で持つ

検査は 2026-11-01 以降の日付の 照合 見出しだけに掛かる（それ以前の節は旧様式のまま残す）。
